MCP · early access

AudioKit for agents

AI agents can use AudioKit through the Model Context Protocol. The MCP server is part of the API: the same API keys, the same validation and the same jobs as /v1, exposed as tools.

MCP is rolling out, in early access like the rest of AudioKit. Until it reaches your base URL, agents can call the HTTP API directly.

{{BASE_URL_NOTE}}

Connect

EndpointPOST {{API_BASE}}/mcp
Transport

MCP Streamable HTTP, on the same host as /v1. Stateless: there is no Mcp-Session-Id, and responses are plain application/json.

Authentication

Your AudioKit API key, as for the HTTP API: Authorization: Bearer <api key>. A missing or unknown key gets HTTP 401 with {"error": {"code": "unauthorized", "message": …}}, before any MCP handling.

Server

Name audiokit, title AudioKit, version = the API version.

Any client that supports Streamable HTTP with a custom header can connect. In a client's JSON config:

mcp config
{
  "mcpServers": {
    "audiokit": {
      "type": "http",
      "url": "{{API_BASE}}/mcp",
      "headers": { "Authorization": "Bearer ak_..." }
    }
  }
}

Or with Claude Code:

shell
claude mcp add --transport http audiokit {{API_BASE}}/mcp \
  --header "Authorization: Bearer ak_..."

Input files

Files are passed as in the HTTP API: an https url AudioKit can download, plus the file's sha256. URLs must resolve to public addresses. See Before you start.

Output

A successful tool result carries the object in structuredContent, and the same object as JSON in its text content. Shapes match the HTTP API exactly: health returns Health, list_operations returns Capabilities, and every job tool returns the Job, as GET /v1/jobs/{id} does:

Job fields
provider_job_id, job_id, operation,
status        queued | running | succeeded | failed | canceled
result, error, provenance,
created_at, started_at, finished_at

Waiting for results

wait_seconds holds the tool call open until the job finishes or the time runs out. It is 60 seconds by default on the analysis tools and 0 on submit_job and get_job, up to 300.

If the time runs out first, the Job comes back queued or running. That isn't an error: call get_job with its provider_job_id, optionally with wait_seconds, until it finishes.

Errors

A refused call is a tool result with isError: true and structuredContent holding the API's error body:

structuredContent
{ "error": { "code": "not_found", "message": "…" } }

The codes are the HTTP API's: invalid_request, operation_unavailable, idempotency_conflict, not_found, rate_limited and unavailable. Every job is checked with billing before it is queued, so submitting one can also return 402 insufficient_credits or no_active_plan, or 503 entitlement_unavailable when the check couldn't be made; nothing was queued in any of those cases. insufficient_credits means the account's prepaid credits don't cover the job: buy a credit pack, or wait for next month's free credits. The meanings of no_active_plan and entitlement_unavailable are in the reference. A missing or unknown key never reaches a tool: it gets HTTP 401 unauthorized, as described under Connect.

A failed job is not a tool error. It comes back as a Job with status: "failed" and error.code set to one of the job error codes.

Consent

list_operations reports requires_consent for each operation. Submitting a consent-gated operation without authorization is refused with invalid_request, through MCP as through /v1.

No operation is consent-gated today. The future voice tools will be.
